# Architecture.md — CentrAlign Autonomous AI Employee Runtime

## 1. Architectural Philosophy

Most AI agent prototypes fail in enterprise production because they treat the Large Language Model (LLM) as the runtime itself—relying on unconstrained prompt loops to remember company rules, enforce permissions, recover from errors, and self-report success.

CentrAlign inverts this model: **the runtime is a deterministic, persistent state machine; the LLM is a bounded reasoning component invoked only for ambiguity resolution, planning, and failure diagnosis.**

| Concern | Naive Agent Wrapper | CentrAlign Operator Runtime |
| :--- | :--- | :--- |
| **Company Context** | Stuffed into system prompts | Structured **Semantic + Episodic Memory** hydrated per task |
| **Parameter Passing** | Regenerated by LLM at every step | Late-bound references (`$working_memory.*`) resolved deterministically |
| **Permissions & Safety** | Prompt instructions ("Do not spend over ₹50k") | Hard **Policy Engine** intercepting tool calls before execution |
| **Error Recovery** | Blind retries or hallucinated fixes | Structured **Observe → Adapt** loop that learns and persists rules |
| **Task Completion** | LLM claims `Task complete!` | **Independent Verifier** checks DB state, files, and DOM screenshots |

## 3. State Machine & Lifecycle Contracts (`core/runtime.py`)

Every run is encapsulated in a serializable `TaskRunState` object. State transitions are strictly directional and logged to `TaskRunState.audit_log`.

### 3.1. State Transition Graph

```text
[GOAL]
  |
  v
[UNDERSTAND] ---> Queries CompanyMemoryStore for aliases, SOPs, policies, and prior lessons
  |
  v
[PLAN] ---------> Generates ordered List[PlanStep] with RiskLevels & VerificationPredicates
  |
  v
[EXECUTE] <----------+
  |                  | (Approved)
  +--> [WAITING_FOR_APPROVAL] ---> (Rejected) ---> [FAILED]
  |                  ^
  v                  |
[OBSERVE]            |
  |                  |
  +--> (Step Error + Recoverable) ---> [ADAPT] ---> Updates Params & Episodic Memory ---> (Back to EXECUTE)
  |
  +--> (Step Error + Max Retries Exhausted) ---> [FAILED]
  |
  v (All PlanSteps Completed)
[VERIFY] -----------> Runs 5 independent checks against Portal DB, FileSystem, and Live DOM
  |
  +--> (All Checks Pass) ---> [COMPLETED]
  +--> (Any Check Fails) ---> [FAILED]
```

### 3.2. Late-Bound Working Memory Resolution

Steps in a plan often depend on outputs produced by earlier steps—for example, `step_3_register_vendor` produces a `vendor_id` required by `step_4_schedule_payout`.

Rather than re-invoking the LLM between every step to rewrite tool payloads, `PlanStep.params` uses deterministic pointer syntax such as:

- `$working_memory.invoice.vendor_name`
- `$working_memory.vendor_id`

Immediately prior to step execution, `Runtime._resolve_params()` traverses `TaskRunState.working_memory` to bind live values into the tool call.

## 4. Organizational Memory Architecture (`core/memory.py`)

Company context is persisted in `./workspace/company_memory.json` and divided into three tiers.

### 4.1. Semantic Memory (Static / Admin-Configured)

- **Directory & Resource Aliases:** Maps human shorthand (for example, `dropbox folder`) to concrete paths such as `./workspace/inbox`.
- **System Endpoints:** Maps logical systems (for example, `finance_portal`) to URLs such as `http://127.0.0.1:8001`.
- **Standard Operating Procedures (SOPs):** Ordered canonical business rules, such as `SOP-FIN-04` for vendor onboarding and invoice payout.

### 4.2. Policy Memory (Governance Rules)

Defines quantitative and categorical guardrails, including `max_autonomous_payout_inr: 50000.0`.

### 4.3. Episodic Memory (Self-Learned Operational Quirks)

Stores `EpisodicLesson` records learned during prior `ADAPT` phases. Example:

```json
{
  "lesson_id": "LSN-001",
  "tool_name": "browser.register_vendor_ui",
  "error_signature": "ERP-422",
  "parameter_name": "tax_id",
  "transformation_rule": "strip_hyphens_and_spaces_uppercase",
  "explanation": "Acme Finance Portal requires 15-char alphanumeric GSTIN without hyphens."
}
```

**Pre-Execution Sanitization Hook:** Before any tool executes, `CompanyMemoryStore.apply_episodic_lessons()` inspects the tool name and parameters, automatically applying known transformations so the agent does not repeat a historical mistake.

## 5. Connector Abstraction & Computer Use (`connectors/`)

All external interactions implement `BaseConnector` (`connectors/base.py`) and return a standardized `ToolResult`:

```python
class ToolResult(BaseModel):
    success: bool
    data: Dict[str, Any] = {}
    error: Optional[str] = None
    error_code: Optional[str] = None
    screenshot_path: Optional[str] = None
```

### 5.1. Browser Connector (`connectors/browser_connector.py`)

Operates the internal Acme Finance Portal (`portal_app/app.py`) using Playwright Chromium.

- **Deterministic DOM Interaction:** Waits for explicit selectors (`#vendor-name`, `#vendor-tax-id`, `#submit-vendor-btn`) rather than brittle sleep timers.
- **Visual Evidence Capture:** Captures full-page screenshots after every form submission (`{evidence_dir}/{step_id}_attempt_{n}.png`), whether it succeeds or fails.
- **Structured DOM Observation:** Inspects `#error-banner` versus `#success-banner` in the rendered HTML response, extracting `data-error-code`, `data-vendor-id`, or `data-payout-id` into `ToolResult`.

### 5.2. File & ERP API Connectors

- **FileConnector** (`connectors/file_connector.py`): Handles atomic file ingestion from `./workspace/inbox/` and post-processing archival into `./workspace/processed/`.
- **ERPConnector** (`connectors/erp_api_connector.py`): Provides fast read-only lookup (`GET /api/lookup_vendor`) and ground-truth state snapshots (`GET /api/verify/state`).

## 6. Self-Healing & Adaptation Pipeline (`OBSERVE → ADAPT`)

When a connector returns `ToolResult(success=False)`, the runtime does not blindly retry with identical arguments.

1. **Failure Inspection:** `Runtime._observe_and_adapt()` captures the error string, error code, and failure screenshot path.
2. **Diagnostic Resolution (`core/llm.py`):**
   - **Live LLM Mode:** The runtime sends the step definition, current parameter payload, and DOM error banner to the LLM with a structured output schema (`AdaptationDecision`) requesting the root cause, repaired parameter value, and reusable transformation rule.
   - **Deterministic Fallback Mode:** The built-in diagnostic rule matches `ERP-422` / `INVALID_TAX_ID`, strips hyphens and spaces from `tax_id`, and emits the `strip_hyphens_and_spaces_uppercase` rule.
3. **Memory Write-Back:** The new `EpisodicLesson` is immediately flushed to `company_memory.json`.
4. **Bounded Retry:** The step is re-queued with the mutated parameters, capped at `max_attempts = 3` per step to prevent infinite loops.

## 7. Independent Verification Engine (`core/verifier.py`)

To prevent an AI employee from hallucinating task completion, `OutcomeVerifier.verify()` executes five independent checks after the plan finishes.

| Check ID | Verification Target | Mechanism | Pass Condition |
| :--- | :--- | :--- | :--- |
| `vendor_persisted` | Portal Database (`GET /api/verify/state`) | HTTP API read | `vendor_id` exists and `tax_id` is 15 alphanumeric characters |
| `payout_scheduled` | Portal Database (`GET /api/verify/state`) | HTTP API read | `payout_id` exists with `state == "SCHEDULED"` |
| `amount_integrity` | Cross-system reconciliation | JSON vs. DB comparison | Scheduled payout `amount_inr` equals source invoice `amount_inr` |
| `file_lifecycle` | Local filesystem (`workspace/`) | Path existence check | Source JSON removed from `inbox/` and present in `processed/` |
| `visual_dom_receipt` | Live Web UI (`GET /`) | Playwright headless read | `#payouts-table` contains `payout_id` and a screenshot is saved |

Only if `all(check.passed for check in checks)` evaluates to `True` does the runtime transition to `RunPhase.COMPLETED`.

## 8. Scaling from Prototype to CentrAlign Production

Although this repository is packaged as a zero-dependency local proof of concept, every boundary is designed to map to an enterprise multi-tenant production stack.

### 8.1. Durable Execution & Background Queues

- **PoC:** In-process state machine with JSON checkpointing (`checkpoint_hitl.json`).
- **Production:** Each `TaskRunState` maps to a Temporal.io workflow or PostgreSQL-backed job queue (`pgmq` / Celery). When a run reaches `WAITING_FOR_APPROVAL`, the worker releases compute resources and resumes through a webhook signal when a human approves in Slack, Teams, or the CentrAlign Web Console.

### 8.2. Isolated Computer-Use Sandboxes

- **PoC:** Local headless Chromium via Playwright.
- **Production:** Ephemeral per-tenant browser containers or Firecracker microVMs, supporting Playwright DOM automation and X11/VNC desktop OS automation, with live video streaming into the operator dashboard.

### 8.3. Hybrid Organizational Memory

- **PoC:** Structured JSON document (`company_memory.json`).
- **Production:** PostgreSQL + pgvector, combining exact policy/RBAC tables with semantic vector search over company wikis (Notion/Confluence) and episodic execution traces scoped by `organization_id`.

### 8.4. Credential Vaulting & Zero-Trust Proxy

- **PoC:** Local environment variables.
- **Production:** Connectors never hold raw credentials; browser sessions and API tokens are injected at the network boundary through short-lived vault leases.
